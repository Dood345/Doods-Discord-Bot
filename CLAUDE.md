# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Dependencies are managed with `uv` (`pyproject.toml` + `uv.lock`; requires Python >=3.14). On this Windows dev machine `uv` is invoked as `python -m uv`.

```bash
python -m uv sync                                   # install deps (incl. dev group)
python -m uv run python main.py                     # run the bot (needs .env)
python -m uv run pytest                             # full test suite (testpaths = tests)
python -m uv run ruff check .                       # lint: F + E9 only (CI runs it too)
python -m uv run pytest tests/utils/test_database.py::test_name -v   # single test
python -m uv run pytest --cov=utils --cov=services  # coverage
python -m uv run python utils/seed_games.py         # seed games table in data/doodlab.db
python -m uv run python utils/verify_db.py          # inspect DB contents
```

`pytest.ini` sets `asyncio_mode = auto` and `pythonpath = .`, so async tests need no decorator. `tests/conftest.py` provides `temp_db` (a `DatabaseHandler` on a tmp SQLite file with tables created) and `mock_config`.

AI tests mock `AIHandler._chat` (agent path) or `AIHandler._generate` (one-shot prompts); never hit a real model in tests. With `OLLAMA_URL` unset the handler starts disabled (`client is None`), so tests set `handler.client = True`.

Slash commands are **not** auto-synced on startup. After adding/changing an `app_commands` command, the owner runs the prefix command `!sync .` (instant, current guild: copies the global commands into it), `!sync` (global, usually minutes), or `!sync clear` (removes the guild copies, e.g. if commands show twice after both) in Discord. The `sync` command is defined inside `main.py`'s `__main__` block.

## Architecture

discord.py bot (`DoodsBot` in `main.py`, a `commands.Bot` subclass). `load_dotenv()` runs **before** `config` is imported because `BotConfig` reads env vars at class-definition time.

Shared singletons are attached to the bot in `DoodsBot.__init__` and accessed by cogs via `self.bot.<name>`:
- `bot.config` — `BotConfig` (`config.py`): `PERSONAS` (characters from `content/personas.json` via `utils/personas.py`: name, emoji, prompt, roast/compliment templates with `{target}`, `in_rotation`; `CHARACTER_PROMPTS`/`CHARACTER_INFO` are derived from it), keyword reactions, homelab service IPs/URLs/API keys, auth (`OWNER_ID`, `ALLOWED_USERS`). `SERVER_CONTEXTS` (per-guild persona text, int guild ID → str) is loaded from the gitignored `data/server_contexts.json` (format: `data/server_contexts.example.json`); missing file → `{}`.
- `bot.db` — `DatabaseHandler` (`utils/database.py`): async `aiosqlite`, opens a new connection per call (30 s busy timeout), default path `data/doodlab.db`, in WAL mode (set by `setup_tables`; readers never wait on a writer). Because of WAL, copy or restore the live DB only with sqlite's backup API, never `cp`. Tables (`gifts`, `ai_history`, `ai_summaries`, `ai_embeddings`, `user_facts`, `games`, `game_ratings`, `tags`, `game_tags`) (and the rest listed in `setup_tables()`) are created there with `CREATE TABLE IF NOT EXISTS`, which never alters an existing table. Changes to existing tables go in `utils/migrations.py`: numbered, idempotent migrations recorded in `schema_version`; a fresh DB is stamped at the latest version, and an existing DB with pending migrations is backed up first (`data/backups/auto-*.db`, newest 5 kept). Every new migration needs a test that upgrades `tests/fixtures/prod_schema_*.sql` (production's real DDL). `utils/reset_game_tables.py` drops the game tables (after a backup); the next start recreates them.
- `bot.dialogue` — `DialogueManager` (`utils/dialogue_manager.py`): static, user-facing strings live in `content/dialogue.json` (tracked and deployed; `data/` is runtime state only) keyed `character -> response_type -> [variants]`; `dialogue.get(char, type, fallback=..., **fmt_kwargs)` picks a random variant and `.format()`s it. Prefer adding strings here over hardcoding them in cogs.
- `bot.gift_service`, `bot.game_service` — service layer (`services/`) wrapping DB + dialogue logic so cogs stay thin. Tests target services and utils, not cogs.
- `bot.ai_handler` — `AIHandler` (`utils/ai_handler.py`).
- `bot.reaction_handler` — keyword emoji reactions from `config.KEYWORD_REACTIONS`.

**Message layouts (Components v2):** `/queue`, `/points`, `/leaderboard`, `/game list`, `/gamenight`, `/printer` and the confirmation cards reply with `discord.ui.LayoutView` cards built by pure functions in `utils/layouts.py` (one accent-coloured `Container`; `card_text(view)` returns the text for tests). A v2 message can't carry `content` or embeds, and is capped at 40 components / 4000 text chars (builders budget with `fit_lines`; `Card` raises if exceeded). Unlike embeds, mentions inside a `TextDisplay` ping, so every card send passes `allowed_mentions=discord.AllowedMentions.none()`. Attachments show via `MediaGallery` with `attachment://<filename>`. Thumbnails only ever use Discord CDN avatars or `i.ytimg.com`, never a LAN/Plex URL. The Test Chamber question stays a classic message with `ChamberButton` DynamicItems.

Unhandled errors from slash commands/context menus (`tree.on_error`), prefix commands and events (`Bot.on_error`) go through `utils/error_reporting.py`: full traceback in the log, the user gets an ephemeral "something broke", and the owner gets a DM (one per distinct error per 15 min, with tokens, keys, URLs and IPs scrubbed).

Cogs live in `commands/`; each module is a discord.py extension (`async def setup(bot)` that `add_cog`s it) and is loaded by `DoodsBot.setup_hook()` from `EXTENSIONS` in `utils/hot_reload.py` (in that order) — a new cog module must be added there (a test checks every `commands/*.py` is listed). Most commands are slash commands (`app_commands`); prefix is `!`.

**Hot reload** (`utils/hot_reload.py`, owner-only prefix command): `!reload <cog>` / `!reload all` / `!reload list` reload cogs live (`reload_extension` rolls back to the old module on failure; the error goes to Discord, the traceback to the log), `!reload service gift|game|music_library` re-imports a stateless service, swaps a fresh instance onto `bot` and reloads the cogs that cache it, `!reload dialogue` re-reads `content/dialogue.json` (refused if it doesn't parse). Music and Voice Cave are refused while the bot is in voice. Reloading a cog doesn't re-import the `services/`/`utils/` modules it imports; stateful services (ai_handler, image_service, points/test_chamber, homelab) need a restart. Cogs must undo in `cog_unload` what `cog_load`/`__init__` set up (loops, dynamic items, tree commands). Changed slash-command signatures still need `!sync .`.

**AI backend:** a local **Ollama** server (`OLLAMA_URL`, model from `OLLAMA_MODEL`, always `think: false`). The default persona is "Cave Johnson" (Portal).
- **Chat (@mention) is an agent.** `AIHandler.get_chat_response` builds a `/api/chat` message list (system persona + `SERVER_CONTEXTS` entry + a clearance line from `is_authorized(user)`, last 10 `ai_history` rows as turns with `model`→`assistant` (longer chit-chat history made the 12B model skip tools), then the user message with any reply context quoted as untrusted and a `queue_song` hint if it contains a YouTube link). It then calls `utils.agent.run_agent`, which loops model → tool calls → results (max 4 rounds, per-tool and overall timeouts). If the loop fails it falls back to one plain chat call. Only the final user/assistant pair is saved to memory. **DMs stay private:** in a server chat, DM-sourced memory (history rows with `guild_id` NULL, the separate `ai_dm_summaries` summary, `ai_embeddings.is_dm`, `user_facts.is_dm`) is left out entirely unless the message explicitly mentions DMs (`DM_REFERENCE`), in which case it's included and labelled `[in DMs]`/`[from DMs]` with a note that the user asked. In DMs everything is visible. After each reply a background job (`_summarize_history`) folds messages older than the prompt window into a per-user rolling summary (`ai_summaries` table, batches of 20, max 800 chars) that is injected as delimited background; the same background job (`_background_memory`) also embeds each user/Cave exchange that has left the window into `ai_embeddings` (unit vectors, `OLLAMA_EMBED_MODEL`, e.g. `nomic-embed-text`, unset = off). Each chat embeds the message (3 s timeout, skipped on failure) and injects the top 3 old exchanges with cosine ≥ 0.62 as quoted background. Embeddings run with `num_gpu: 0`; the Ollama host needs `OLLAMA_MAX_LOADED_MODELS=2` or every embed evicts the chat model (6–8 s reload). An autouse fixture disables the background job unless a test is marked `real_summaries`. **Card-only replies:** for @mentions (`card_only_ok=True`, set by `answer_mention`), a turn that posted a confirm card (`ToolContext.cards`, filled by `post_confirmation`) returns `CARD_ONLY`: nothing else is posted and memory records `[Posted a confirm button: …]`, unless the message asks for Cave's take (`ASKS_OPINION`). Slash commands, context menus and `/speak` still get the text. **Missed mentions** (`services/ai_backlog.py`, `bot.ai_backlog`): `on_message` runs `answer_mention`; when the model fails, the user sees the "confused processing noises" reply and the message's IDs (never its text) go into `ai_backlog` (max 10, 3 per user, 6 h). They're answered oldest-first, as replies with a "catching up" note, after the next reply that works (`after_success`, which first drops the user's re-asks of the same text) or when the 30 s `ai_catch_up` loop in `commands/maintenance.py` sees Ollama's `/api/version` answering (backoff 1→2→5→10 min while down). Catch-up calls pass `late_since` (the model is told the message is late; `STALE_TOOLS` like `skip_song` are withheld via `ToolContext.blocked`), re-fetch the message (edits/deletes respected), and a message that fails 3 times is dropped. Replies stream: `get_chat_response(on_text=...)` streams Ollama tokens and `utils/streaming.ReplyStreamer` posts after ~40 chars and edits at most every 1.5 s. 3 s per-user cooldown. Tool-enabled calls run at temperature 0.3 and the system prompt has an explicit intent→tool routing list; after changing the prompt or model, re-measure routing with a scripted benchmark against the real model (realistic chit-chat history matters).
- **Tools** live in `utils/agent_tools.py` (`build_cave_tools()`), each a thin wrapper over a service. `requires_auth` tools are hidden from unauthorized callers *and* re-checked at dispatch against `ToolContext.user` (the real Discord author, from `on_message`); `requires_guild` tools are unavailable in DMs. Tool output is read aloud in public channels, so it must never contain IPs/hostnames/keys.
- Side-effecting tools (`add_game`, `queue_song`, `request_media`) never act at tool time: they call `utils.confirm.post_confirmation`, which posts a `ConfirmView` card only the invoking user can click (120 s expiry, optional re-check on click) and returns a `PENDING` note so the model tells the user to click. `remember_fact` writes to the `user_facts` table (max 20/user), which is injected into the system prompt as delimited notes; `/memory` shows them and `/clearhistory` wipes them. Deliberate exceptions that act directly: `rate_game` (only the caller's own, overwritable score; loose titles are resolved to one library game or the model is told to ask) and `skip_song` (caller must be in the music's voice channel, same as `/skip`; both go through `MusicCommands.skip_current`).
- `queue_song` goes through `MusicCommands.resolve_request`/`enqueue_tracks` (see Song routing below; links must be YouTube hosts since yt-dlp runs inside the LAN; won't hijack a session in another voice channel). `play_next` takes a `Guild`.
- Message context menus (`commands/context_menus.py`): "Ask Cave about this" (modal question, then the normal agent path with the message as quoted reply context and tools gated on the clicker), "Roast this", "Fact-check (Dale edition)". Context menus are registered on `bot.tree` in `cog_load` and need a `!sync` like slash commands.
- `/debate` (`services/debate_service.py`) runs two personas for 3 rounds through `AIHandler.complete` (one debate per channel; the user's topic is quoted as data), then posts a native `discord.Poll`.
- One-shot prompts (character commands, roast/compliment, beer, image-prompt enhancement) still use `_generate` on `/api/generate`. Character commands fall back to `dialogue.json` `fallback` entries when AI fails.
- Tests mock `AIHandler._chat` (agent path) or `_generate` (one-shot path); see `tests/utils/test_agent.py` for the scripted-model pattern.

**Store links** (#103): `services/store_lookup.py` (via `GameService.details_from_link`) fills `/game add link:` and Cave's `add_game(link=...)` from Steam's public store API (title, player count parsed from the description or guessed, genres/co-op tags, release state, review summary + Metacritic). It only ever requests `store.steampowered.com`, never the user's URL (the bot is inside the LAN); Epic pages are bot-protected, so Epic links are matched to Steam by exact name, falling back to the title from the slug.

**Steam import**: `python -m utils.import_steam_library [--dry-run] [--all]` (run on the server from the repo root) adds the owner's Steam games (`STEAM_API_KEY`, `STEAM_ID`, public game details) to the shared library (guild_id 0) via `services/steam_library.py`: multiplayer/co-op only unless `--all`, status from playtime, details from the store lookup, cached in `data/steam_import_cache.json` and spaced 3 s apart for Steam's rate limit. Re-runs skip titles already in the library.

**Science Points** (`services/points_service.py`, `bot.points_service`): per-server append-only ledger (`science_points`, unique `award_key` so every award is idempotent) + `achievements` (rules in `content/achievements.json`: `points` totals or `reason_count` by reason prefix). Off per server until a manager runs `/sciencepoints on` (or `/testchamber channel`, which turns it on since trivia pays points); the flag is `guild_settings` key `science_points`, cached in `PointsService.is_enabled`. When on, `on_message` awards +1 for a user's first message per server per local day (`BOT_TIMEZONE`, default America/Chicago; needs `tzdata` on Windows) and reacts 🏆 on a new achievement. `/points`, `/leaderboard` (no pings), and Cave's read-only `science_points` tool. Future awards (e.g. game night) go through `PointsService.award` with a unique key.

**Daily Test Chamber** (`services/test_chamber_service.py` = `bot.test_chamber`, `commands/test_chamber.py`): opt-in per server via `/testchamber channel|off|now` (manage_guild; stored in `guild_settings`, never in the repo). A 2-minute `tasks.loop` posts one Open Trivia DB question per opted-in server at 18:00 local (shared across servers, fallback bank `content/trivia_fallback.json`) and closes it 20 h later: first correct +10, others +3, Cave announces via `AIHandler.complete`. All state is in `trivia_questions`/`trivia_answers`, and answer buttons are a `DynamicItem` (`tc:<qid>:<choice>`), so restarts/deploys lose nothing.

**Game night** (`commands/game_night.py`, `services/game_night_service.py`): `/gamenight start: players: channel:` picks 3 library games that fit the head count (default: humans in the caller's voice channel), rating-weighted and skipping `avoid`, posts a Cave intro + poll, and creates a voice-channel scheduled event (the bot needs Manage Events; it degrades to a note without it). With a voice channel it also records the night (`game_nights`): a 2-minute loop counts who's in that channel from 15 min before the start to 4 h after, and 10 sightings (~20 min) pays `ATTEND_POINTS` once per user per server per local day (`gamenight:<guild>:<date>:<user>` award key; overlapping `/gamenight` runs for one channel reuse the night; qualified users are re-awarded every check, so a failed award retries) in servers with Science Points on; when the window ends it posts one no-ping summary where `/gamenight` ran.

**Facility announcements** (`commands/announcements.py`, `services/announcement_service.py`): opt-in per server with `/announcements channel|off` (`guild_settings`). A 2-minute loop posts newly available Overseerr requests (titles only; the first run silently records the backlog), birthday shout-outs after 9 am local for users who ran `/birthday set` (month/day only, per server, pings only that user), and DMs the owner when a print goes printing -> complete (with webcam snapshot). `announced` makes every announcement once-only across restarts. Without the members intent the member cache is sparse, so look users up with `utils.members.find_member`/`member_name` (cache, then API).

**Voice Cave** (`commands/voice_cave.py`): `/speak prompt:` runs the normal agent path, posts the text, then speaks it with edge-tts (`MUSIC_TTS_VOICE`) in the caller's voice channel via a temp mp3. Refuses to talk over music, one speech per server, disconnects afterwards if it joined only to speak. If edge-tts starts failing with 403, upgrade it (`uv lock --upgrade-package edge-tts`): Microsoft rotates its token.

**3D printer** (`services/printer_service.py`, `bot.homelab_service.printer`): Klipper + Moonraker (Mainsail/FreeDi) from just `PRINTER_IP` + `PRINTER_PORT` (default 80 via Mainsail, 7125 for Moonraker directly; a legacy `PRINTER_HOST=ip:port` still works). Status parses `print_stats`/`display_status`/heaters/filament sensor into progress, time left, layers and temps; webcams are discovered from `/server/webcams/list` (`PRINTER_WEBCAM_URL` only overrides). Stills come from the snapshot URL; `/printer video:true` records a 6 s MP4 from the MJPEG stream with ffmpeg (Discord can't play the stream, and linking it would expose a LAN address). The print-ended DM (announcements) fires on complete, error or cancelled and uses Moonraker's job history.

**Homelab cog** (`commands/homelab_commands.py`): `/printer`, service pings, Overseerr/Sonarr/Radarr/Lidarr. Every command must call `await self.check_auth(interaction)` (owner ID or username in `ALLOWED_USERS`).

**Image generation**: `services/image_service.py` (`bot.image_service`) is shared by `/imagine` and Cave's `generate_image` tool. It allows one job at a time (ComfyUI and Ollama share the GPU), a 60 s per-user cooldown, runs the prompt through `AIHandler.enhance_image_prompt` (safety check + enhancement; `fail_closed=True` for chat-initiated images so an Ollama failure refuses instead of passing the raw prompt), then calls `utils/image_gen.py` (ComfyUI at `COMFY_URL`, workflow `utils/image_z_image_turbo.json` (models from the Comfy-Org/z_image_turbo Hugging Face repo: `z_image_turbo_int8_convrot` (fits the 10 GB card; bf16 doesn't and takes minutes), `qwen_3_4b_fp8_mixed`, `ae`; keep them on the NVMe, a cold load from the HDD takes minutes; the service unloads Ollama's chat model before each job and calls ComfyUI's `/free` after, since both can't share the GPU; ComfyUI must run with `--listen 0.0.0.0 --port 8000` so the server can reach it), blocking calls in a thread, 180 s websocket timeout). The chat tool runs the job in the background and returns `STARTED`. `/portrait` and `/poster` reuse the service and add text with Pillow (`utils/image_compose.py`), since generated lettering is unreliable; the portrait prompt never includes anything about the person, and the badge number is a hash, never the Discord ID.

**Music** (`commands/music.py`): yt-dlp + ffmpeg (must be on PATH) voice playback via `FFmpegOpusAudio` (ffmpeg applies volume and encodes Opus once at `MUSIC_BITRATE`), `edge-tts` announcements. YouTube access needs three things on the server, all wired through `YDL_OPTIONS`:
- `cookiefile`: `www.youtube.com_cookies.txt` in the repo root (untracked, preserved by deploy; export from a private window and close it without logging out). Note the Python option is `cookiefile`, not `cookies`.
- a JS runtime for YouTube's challenges: `yt-dlp[default]` (pulls in `yt-dlp-ejs`) + Deno from the `deno` PyPI package (`_js_runtimes()`); the server's Node 20 is too old for yt-dlp's solver.
- PO tokens from the bgutil provider container (plugin `bgutil-ytdlp-pot-provider`, URL `YT_POT_PROVIDER_URL`). Recreate it on the server with `docker run -d --name bgutil-provider --restart unless-stopped -p 127.0.0.1:4416:4416 brainicism/bgutil-ytdlp-pot-provider`.
**Song routing** (`MusicCommands.resolve_request` → `MusicLibrary.plan`, used by Cave's `queue_song` and by `/play` for plain search terms): a request that is just an artist in the library queues a shuffled 10-track mix (or a 15-track radio when `radio=true` or the artist has < 5 tracks); `radio=true` on a song seeds a radio with it. Radios take ~1/3 from the artist and the rest from Plex's `/similar` artists in the library. Single tracks follow `resolve_track`: YouTube links play from YouTube; any other request tries the owner's Plex library first (`services/music_library.py`, `bot.music_library`: `/hubs/search`, best track by word-match score ≥ 0.6, or a random track when the request names an artist; needs `PLEX_TOKEN`, `PLEX_URL` defaults to `http://PLEX_IP:32400`; queue URLs are `plex:/library/parts/...` and stream with the token in an ffmpeg header), then SoundCloud (`scsearch5`, originals preferred over remixes/covers/live unless asked; `[PREVIEW]` snippets skipped and up to 3 candidates fully extracted so DRM-locked Go+ tracks are passed over), then a YouTube search. `/play` links and `playlist-only` searches still go straight to YouTube.
**Resume after restarts** (`services/music_sessions.py`): the music cog snapshots every connected player (current track, position, queue, paused, notify channel) to `music_sessions` every 10 s; the table always mirrors the live players, so `/stop` or an empty queue removes a session. On startup the save loop first resumes sessions younger than 30 min whose voice channel still has people in it: rejoin, seek to the saved position minus 3 s via `seek_position`, re-pause if it was paused, and post a note. `cog_unload` cancels the loop before clearing players so the last snapshot survives shutdown.
**Controls and leaving:** the `/queue` card (`build_queue_card`) carries ⏮️ Restart / ⏯️ Pause / ⏭️ Skip buttons while something is on: `MusicButton` is a `DynamicItem` (`mc:<action>`, registered in `cog_load`), works only for people in Cave's voice channel, and refreshes the card in place. `on_voice_state_update` → `check_alone`: when the last human leaves Cave's channel he pauses (`auto_paused`), resumes when someone comes back (a manual pause stays paused), and disconnects after `ALONE_TIMEOUT` (10 min) alone, keeping the queue for the next request.
**Resume:** Cave's `resume_music` tool (acts directly, like `skip_song`; withheld for late catch-up replies) and `/play-pause` when nothing is connected both go through `MusicCommands.resume_for`: unpause, or rejoin the member's voice channel with the left-behind player (any channel in that server) and seek back to where it stopped; it says so when there's nothing to resume. **Per-server settings** (manage_guild, `guild_settings`): `/queue-expiry days:` (how long a left-behind queue is kept, default 1 day, `QUEUE_DAYS_KEY`) and `/reboot-messages` (opt-in; off by default, the after-restart "picking up at" note is only posted where it's on).
**Request placement** (`place_request`): while music plays (or is paused) a request joins the end of the queue; when idle (finished, or voice dropped and the bot rejoins) it plays immediately, followed by the song that was cut off and the rest of the old queue, and the reply says so. Replies are built from what actually started (Cave repeats them). A player that lost voice and has been unused for 24 h (`QUEUE_TTL`) is dropped by the save loop, and a day-old leftover queue is discarded on the next request.

## Privacy rules (repo is public)

Never commit real Discord guild/user/channel IDs, LAN IPs/hostnames, friends' names, or homelab URLs. Real values go in `.env` (documented in `.env.example`) or private files under `data/` (gitignored, and preserved on the server because deploy excludes `data/`). CI's privacy-guard step fails on 17–20 digit numbers and `192.168.x.x` in tracked files. Any new feature toggle also belongs in `utils/config_report.py` (startup on/off log). Any new env var must be added to `.env.example` and the user told to add it to the server's `.env` before merging to `main`.

## Deployment / CI

- Push to `main` → `.github/workflows/deploy.yml` on a self-hosted runner: snapshots the running release (code + venv) to `<DEPLOY_PATH>.prev`, rsyncs the repo to `DEPLOY_PATH` (repo variable, default `/home/dood345/discordBot`; excluding `.env`, `data/`, `venv`, cookies file), runs `uv sync --no-dev`, restarts `discordBot.service`, then waits up to 180 s for `data/ready.json` (written in `on_ready` by `commands/maintenance.py`) to be newer than the restart. If it isn't, the job restores `.prev`, restarts, and fails red. Run the workflow manually with `simulate_failure` to exercise the rollback. The server reboots itself at 03:30 after kernel upgrades (unattended-upgrades), so `discordBot.service` must be enabled at boot (`sudo systemctl enable`; the deploy warns when it isn't): `Restart=always` only covers crashes. The runner only has passwordless `sudo systemctl restart discordBot.service`. `commands/maintenance.py` also writes a nightly DB backup at 03:00 local (`data/backups/auto-nightly-*.db`, 14 kept; one at startup if the newest is >26 h old). Anything under `data/` (DB, logs, `server_contexts.json`) is server-local and never deployed; tracked content like dialogue lives in `content/`.
- PRs to `main`/`dev` → `build.yml`: `uv sync`, compileall, `pytest`, privacy guard.
- Workflow is feature branch → `dev` → `main`. Never push straight to `main` (it deploys).
- Overhaul roadmap and per-phase kickoff prompts: `docs/ROADMAP.md`.
